1. 設計原理と不変条件

apparness の差別化は「実行結果の内容そのものを機械が検証する」点にある。 AI の自己申告（self-review / 自己宣言）をゲートの根拠に採らない。この原理から次の不変条件が導かれる。 改修時にこれらを壊す変更は、どれだけ有益に見えても却下する。

INV — 壊してはならない性質

INV-1AI の自己申告を根拠にしたゲートを新設しない
INV-2受領書（verification_receipt / 統合受領書）を人間・AI が手書きできるようにしない
INV-3受領書の commit と HEAD の一致条件（CI では祖先＋未変更の等価条件）を緩めない
INV-4Bash 経由の間接書き込み検知・危険操作検知に、解除用の環境変数を追加しない
INV-5harness/hooks/** は Python 標準ライブラリのみで動く状態を維持する
INV-6gate-reviewer の verdict は深刻度の機械的集計のみで決める。Write/Edit を与えない
INV-7スタック固有の標準をハーネス本体に規定しない

INV-5 は監査可能性の根拠でもある。harness/hooks/ 配下の全 *.py の import は AST 解析で標準ライブラリのみであることを確認済み（唯一の例外は post_tool_use_guard.py → pre_tool_use_guard.py の兄弟 import）。

3. Hook — 介入点と exit code 契約

登録は .claude/settings.json。Hook は exit 2 = 拒否、それ以外 = 「判断なし＝通過」 として扱われる。この非対称性が後述の fail-open 問題を生む。

パス解決の 2 段階

Rule 適用前に、書き込み先を必ず次の順で正規化する。どちらか一方でも欠けると Rule 群がまとめて素通りする。

  1. path_utils.resolve_write_target(target, cwd, toplevel) — そのパスが属するリポジトリのルートを基準に相対化。相対パスは cwd 基準で解決する （セッションの cwd は worktree ルートとは限らない）。リポジトリ外（/tmp 等）は対象外。
  2. path_utils.resolve_worktree_scope(rel_path, toplevel) — ^apps/[^/]+/\.worktrees/[^/]+/ の接頭辞を再帰的に剥がし、基準ルートも同時に読み替える。 剥がすだけでは各 Rule が os.path.join(toplevel, rel_path) で参照する status.yaml / contract.yaml / shared-kernel.yaml が別ファイルを指す。

fail-open — 構造的に残る穴（docs/HARNESS_GUIDE.md 11節 A-1）

Hook を起動するのは Claude Code である。python3 不在・import 失敗・タイムアウトの いずれでも Hook は exit != 2 で終わり、Rule 1–12 が黙って無効化された状態で作業が継続する。 ハーネス側からこの失敗を止める手段はない（失敗しているのは自分自身）。

緩和は 3 点のみ: ①fail-closed（判定に到達したうえでの例外に加え、hook の入力を解釈できない場合も通さず exit 2。stop_commit_guard.py にも適用） ②SessionStart 自己診断（hooks の import 可否・path_utils の必須関数 8 つ・ settings.json の 5 登録を検査。正常時 53ms・無出力） ③PROGRESS.md 先頭への状態表示。 再検討の条件: Claude Code が Hook 起動失敗時の fail-closed を既定提供したとき。

ask ではなく deny を採る理由（NG-6）

AUTONOMOUS モードでは AI 自身が確認プロンプトに答えてしまうため、ask は歯止めにならない。 人間の判断を挟みたい操作は deny にしたうえで「人間が別途手で実行する」運用に倒す。 また INV-4 によりバイパス用環境変数を持たないため、誤検知は検知ロジック側を修正して解消する。

判定不能時の挙動 — undecidable → allow（fail-closed と対になる方針）

「例外」と「判定不能」は挙動が逆である。これは監査上いちばん誤解されやすい点なので明示する。 分かれ目は判定の入口か、判定の材料かである。入口（hook の入力そのもの）が壊れている場合は 判定に着手すらできないので deny、入口は正常だが材料（対応する status.yaml・shared-kernel.yaml・git 情報など）が存在しない場合は allow に倒れる。

  • 例外（判定に到達したが壊れた）→ deny。 _fail_closed_main() が exit 2 ＋ 理由を返す。
  • 判定不能（判定に必要な材料が存在しない）→ allow。 各 check 関数が None を返す。Hook は「材料が無いから止める」ことをしない。

後者は pre_tool_use_guard.py 内に 8 条件、path_utils.py 内にさらに数条件ある。 これらは Rule が意図的に空振りする経路であり、監査時に最初に確認すべき点である。

この方針の代償と、埋め合わせ

「材料が無ければ通す」は、材料を消せばゲートを外せることを意味する （例: shared-kernel.yaml を消せば Rule 5 は発火しない）。 Hook 単体ではこれを塞げないため、CI 側は逆に「無ければ違反」で判定する—— 項目 I は test_command がどこにも宣言されていないのに TESTED/INTEGRATED なら不合格にし、項目 A はスキーマ必須キーの欠落を弾く。 Hook（未然・寛容）と CI（事後・厳格）の非対称は意図的である。

Rule ごとのツール適用範囲

PreToolUse の matcher は 7 ツールだが、全 Rule が全ツールに適用されるわけではない。 内容比較に依存する Rule 3・7・9・10・11 は run_checks() 内で tool_name in CONTENT_SIMULATABLE_TOOLS（＝ Edit/Write/MultiEdit）に 限定されている。

この限定はそのままでは穴になる。実測で 3 件の素通りを確認した: ①NotebookEdit で受領書なしの state: TESTED が書けた （simulate_write_result() が NotebookEdit を扱えず、書き込み後の内容として変更前の内容が そのまま返るため、Rule 9・10 から見れば「何も変わっていない」） ②Bash で integration.machine.yaml を書けた（統合受領書の手書き ＝ INV-2 違反） ③NotebookEdit でも同じ。

対処として、判定を「Bash かどうか」ではなく「書き込み後の内容を再現できる手段かどうか」に 一般化した（check_requires_simulatable_tool()）。 CONTENT_JUDGED_RES に integration.machine.yaml を追加し、 CONTENT_SIMULATABLE_TOOLS に無いツールは自動的に拒否側へ入る （将来ツールが増えても既定で安全側）。

この制限を事後検証には掛けない（掛けると受領書が消える）

check_requires_simulatable_tool() は tool_name が空のとき判定しない。 事後検証（post_tool_use_guard.py）は run_checks() を tool_name なしで呼び、 「実際に何が変わったか」を見る経路だからである。そこには run_verification.py が 書き込んだ受領書——実行の裏付けを伴う正規の書き込み——も含まれる。ここで拒否側に倒すと 受領書そのものが巻き戻され、TESTED へ永久に進めなくなる。 この逃がしは test_post_tool_use_guard.py::test_a_harness_script_writing_the_receipt_is_not_reverted が固定している。

Bash 経由書き込みの 2 段検知

  • 静的検知: extract_bash_candidate_paths()。shlex（posix / punctuation_chars）で トークン化し、>/>> のリダイレクト先と cp/mv/tee/sed -i の対象を抽出。 トークン化前に _classify_bash_lines() がクォート・行継続・ヒアドキュメントを考慮して改行を ; に正規化する。 ヒアドキュメント本体は「データ」として抽出対象から除外（本体の内容を空にし、行自体は残してコマンド境界を保つ）。 除外は本体のみで、cat > path <<EOF のリダイレクト先は従来どおり抽出する。
  • 事後検証: post_tool_use_guard.py。Bash 実行直前に capture_worktree_state() で 未コミットパスの {code, sha, text} を保存し、実行後に内容の SHA-1 で比較して差分を検出、 restore_from_snapshot() で実行直前の内容へ復元する（HEAD ではない ＝ 人間の未コミット編集を巻き添えにしない）。 状態コードではなく内容ハッシュで比較するのは、git add だけで ' M' → 'M ' と変わり誤発火するため（F-050）。

6. コンテキスト予算 — 実測と計上規則

規範は CONVENTIONS.md 15節、強制は ci_check.py の項目 L。 上限は CONVENTIONS.md 36,000 / agent 各 12,000 / 1 セッション合計 46,000 バイト。

計上式

session_total(agent)
  = sizeof(.claude/agents/<agent>.md)
  + attributed_conventions_bytes()   # マーカー宣言された CONVENTIONS.md の節のみ
  + always_read_bytes()              # マーカー宣言された harness/procedures/*.md
<!-- context-budget: conventions-sections=6,9,10,11,12,13,14 -->
<!-- context-budget: always-reads=harness/procedures/feature-build.md -->

conventions-sections マーカーが無い agent は「CONVENTIONS.md を全文読む」とみなし ファイル全体を安全側で計上する。none は 0 バイト。 harness/procedures/*.md への言及があるのに always-reads 宣言が無い場合は不合格 （check_undeclared_procedure_reads()）。これが無いと、プロンプト本文を別ファイルへ移して 「起動直後に読め」と書くだけで測定値だけが改善し、実コストは変わらない（＝空洞化する）。

9. ゲート判定の書式と決定性

状態機械（status.yaml.state）

NOT_STARTED → CONTRACT_DRAFTED → CONTRACT_APPROVED → IN_PROGRESS → IMPLEMENTED → TESTED → INTEGRATED
                                  ＋ BLOCKED（一時停止 / どの非終端からでも可）
                                  ＋ SUPERSEDED（終端 / どの非終端からでも可）

直線状態は 1 段階前進のみ。BLOCKED からの復帰は resolve_effective_previous_state() が state_history[] を at の昇順（安定ソート）で遡り、直前の非 BLOCKED 状態から 判定し直す。これが無いと IN_PROGRESS → BLOCKED → INTEGRATED が通る。

検証受領書（Rule 10 の根拠・手書き不可）

生成は run_verification.py のみ。宣言は shared-kernel.yaml（全機能共通）を contract.yaml（機能個別）がキー単位で上書きする（merge_verification_declaration()）。 

# 宣言（設計フェーズ）
verification:
  working_dir:       "src"
  test_command:      "pytest -q --junitxml=../.verify/junit.xml"   # 必須
  build_command:     "python -m build"                             # 以下は任意
  typecheck_command: "mypy src"
  lint_command:      "ruff check --select E,F,I ."
  junit_xml:         "../.verify/junit.xml"
  max_skip_ratio:    0.2

# 受領書（status.yaml へ機械が書き込む。schema: additionalProperties: false）
verification_receipt:
  commit: "<40 桁 SHA>"                    # required / minLength 7
  test:      { exit_code: 0, at: "…Z", tests: 42, failures: 0, errors: 0, skipped: 1 }
  build:     { exit_code: 0, at: "…Z" }
  typecheck: { exit_code: 0, at: "…Z" }
  lint:      { exit_code: 0, at: "…Z" }
  traceability: { declared: 5, matched: 5, missing: [], failed: [] }

commit 一致条件が本質（INV-3）

受領書は「そのコミットの状態で通った」という主張であり、実装が進めば無効になる。 この条件が無ければ実装を書き換えた後も過去の成功記録を使い回せる。 CI（項目 I）は HEAD が先に進んでいるため等価条件に置換する: ①receipt.commit が HEAD の祖先（git merge-base --is-ancestor） ②commit〜HEAD の間に機能ディレクトリ（status.yaml を除く）が未変更 ③宣言コマンドの exit_code と JUnit 集計。

独立レビュー記録（記録であって証明ではない）

review:
  verdict:  GO           # enum: GO | NO-GO | ESCALATED   ← 3R 収束せず人間へ委ねた状態
  at:       "2026-08-24T10:00:00Z"
  rounds:   2            # required
  blockers: 0            # integer（Blocker ≥ 1 → 自動的に NO-GO）
  majors:   1            # integer
  minors:   3            # integer
  notes:    "Major: …"   # 指摘本文は文字列 1 本にまとめる

blockers/majors/minors は件数（integer）であり、 指摘の本文を文字列配列として書くと schema 違反になる（F-062）。 verdict は深刻度集計から機械的に決まる（INV-6）が、受領書と違い実行の裏付けを持たないため 機械的ゲートにはしない。
