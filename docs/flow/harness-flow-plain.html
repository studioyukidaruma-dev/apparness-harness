1. そもそも何をする仕組みか

このハーネスは、AI にアプリを作らせるときの「工程管理」と「品質の下限」を、機械が強制する仕組みです。 ふつうの開発ルールは「守りましょう」と書いてあるだけですが、ここでは破ろうとした操作そのものが実行前に止まります。

いちばん大事な考え方

「やりました」という AI の自己申告を、根拠にしない。
たとえば「テストを書いて通しました」は信じません。代わりに、機械がテストコマンドを実際に実行して、 その結果（終了コード）を記録した受領書を作り、受領書が無ければ「テスト完了」の状態に進めません。 受領書は人にも AI にも手書きできないようになっています。

作られるアプリは apps/<アプリ名>/ の下に置かれ、次の 5 段階で進みます。

  1. 要件定義 ― 何を作るかを決める（00-requirements/）
  2. 共通の土台 ― 全機能が共通で使う約束事を決める（01-foundation/）
  3. 設計 ― 独立した機能に分割する（02-design/）
  4. 機能ごとの実装 ― 機能 1 つにつき作業場所を 1 つ用意して並行実装（03-features/）
  5. 組み上げ ― 機能どうしをつないで完成させる（04-integration/）

見張り（フック）― 5 つのタイミング

タイミングプログラム何をするか制限時間
会話を始めたときsession_start_healthcheck.py 見張りの仕組み自体が壊れていないか自己診断。壊れていれば警告し、「この会話では強制が効いていない」と AI にも伝える5 秒
ファイルを読み書きする直前pre_tool_use_guard.py 12 の規則に照らして、ダメなら実行させない。ここが本体5 秒

返事を終えようとしたときstop_commit_guard.py 大事な記録の保存漏れがあれば終了させない5 秒

見張りが「効かなくなる」ことがある、という話

見張りを呼ぶのは Claude Code 側です。もし Python が見つからないなどで見張りが起動に失敗すると、 Claude Code はそれを「問題なし」と解釈して通してしまいます。 つまり全部の規則が黙って無効になった状態で作業が続きます。

これはハーネス側からは止められません。できるのは気づけるようにすることだけなので、 ①会話の開始時に自己診断する ②進捗ダッシュボードの先頭に「見張りの状態」を出す ③見張り自身が想定外のエラーで落ちたときは「通す」ではなく「止める」（安全側に倒す） の 3 つを入れています。

担当者（エージェント）― 5 人

担当者担当する工程できることできないこと
requirements-analyst要件定義人と対話して要件をまとめる承認を自分で書けない（承認は親のセッションが書く）
solution-architect土台・設計機能分割・技術選定・検証コマンドの宣言実装はしない
feature-builder機能 1 つの実装自分の機能フォルダの中だけ書き換え他機能・設計・ハーネス本体は書けない
gate-reviewer実装の第三者点検読む・調べる・判定する書き換えられない（道具として渡していない）
integrator組み上げ各機能をつないで結合テスト他機能の中身は直せない

手順書（スキル）― 4 つ

スキルいつ使うか何をするか
init-app「新しいアプリを作りたい」フォルダの雛形を作り、要件定義の担当者に引き継ぐ。企画ブリーフ（後述）があれば、それを要件定義の出発点にする
new-feature-worktree機能の実装に着手するときその機能専用の作業場所と雛形を作る
sync-progress進捗を見たいときダッシュボードを作り直す（--html で見やすい画面も出せる）
diff-design「仕様を変えたい」要件を新しい版として書き直し、設計の差分を機械的に出す

先に伝えたいことを書いておく（企画ブリーフ・任意）

対話で少しずつ聞かれるのが面倒なとき、目的・ほしい機能・使ってほしい技術などを 先に 1 枚のファイルに書いて渡せます。briefs/<アプリID>.brief.yaml に置いておくと、 init-app が自動で見つけて要件定義の出発点にします。

  • 書けるところだけ書けば十分です。空欄は対話で聞かれます（勝手に埋められません）
  • 逆に、書いた項目は聞き直されません
  • 項目名を書き間違えると、確認コマンド（check_brief.py）がエラーで止めます。 「書いたのに伝わっていなかった」を防ぐためです
  • ブリーフを書いても、要件の承認は今までどおり人が行います

4. いつ何が動くのか（時間順）

会話を 1 回始めてから終わるまで

  1. 開始 ― 見張りの自己診断が走る（0.05 秒くらい。異常がなければ何も表示されない）
  2. AI が考える ― ここには誰も介入しない
  3. AI がファイルを読もう／書こうとする ― 直前に見張りが判定。ダメなら実行されず、AI には「なぜ止まったか」と「正しい進み方」が返る
  4. 書けた場合 ― 直後に進捗ダッシュボードが自動で作り直される
  5. コマンドを実行した場合 ― 直後に「事前チェックをすり抜けた書き込みが無いか」を実際のファイル内容で確認し、あれば元に戻す
  6. 返事を終えようとする ― 大事な記録に保存漏れがあれば終了を拒否され、保存してからでないと終われない

アプリを 1 本作り終えるまで

  1. （任意）企画ブリーフを先に書く → init-app で雛形を作る → requirements-analyst が要件をまとめる → 人が承認
  2. solution-architect が土台と設計を作る → 承認
  3. 機能ごとに new-feature-worktree → feature-builder が実装
    • 実装が終わったら code-review（自己点検）
    • 次に gate-reviewer（別の担当者による第三者点検）
    • 最後に検証スクリプトを実行して受領書を作る
    • 受領書ができて初めて「テスト完了」にできる
  4. 全機能が「テスト完了」になったら integrator が組み上げ、つなぎ目のテストを実行
  5. GitHub に push すると CI が 16 項目を再チェック

6. 文書の役割分担 ― 書き足すときはどこへ

同じことを 2 箇所に書かないのが、この仕組みの一貫した方針です。 2 箇所にあると必ず片方だけ直されて食い違うからです（実際に起きて、手順どおりやると機械に拒否される状態になりました）。 食い違いは CI が機械的に検出します。

迷ったときの 3 つの質問

  2. 「なぜ」の話か？ → はい なら docs/HARNESS_GUIDE.md
  3. 特定の担当者の作業手順か？ → はい なら その指示書か procedures/

7. git のブランチと「触ってよい場所」

ブランチの名前は 4 種類だけ

用途名前の形例そこで触れる場所
アプリの雛形作りapp/<アプリ名>/bootstrapapp/todo/bootstrapそのアプリのフォルダ
機能の実装feature/<アプリ名>/<機能名>feature/todo/todo-list-apiその機能のフォルダだけ
ハーネス本体の改修harness/<内容>harness/fix-guardハーネス本体を触れる唯一の場所
組み上げ（任意）integration/<アプリ名>integration/todo組み上げフォルダ

保護のかかり方

保護される場所誰なら書けるか止めるもの
harness/ .claude/ .github/
（＝ハーネス本体）		 harness/ で始まるブランチにいるときだけ
（例外: .claude/settings.local.json は個人設定なのでいつでも可）		 規則1（実行前）＋ CI の項目 B（push 後）
他の機能のフォルダ その機能専用の作業場所にいるときだけ
（status.yaml だけは例外）		 規則2 ＋ CI の項目 C
要件・土台・設計の文書 機能実装用の作業場所からは書けない 規則6
承認済みの契約書 誰も書き換えられない（追記だけ可） 規則3 ＋ CI の項目 D

逃げ道は 1 つだけ、しかも記録が残ります

ハーネス本体の保護（規則1）だけは、HARNESS_UNLOCK=1 という設定で一時的に外せます。 外すと警告が出ます。ふだんの運用では使いません。
それ以外の規則（とくにコマンド経由の書き込み検知や危険操作の拒否）には、解除するしくみを意図的に作っていません。 AI が自分で解除できてしまったら、「機械が強制する」という前提そのものが崩れるからです。 誤って止まる場合は、設定で逃げるのではなく検知のプログラム自体を直します。

「作業場所（worktree）」について

機能を並行して作るために、機能 1 つにつき git の作業場所を 1 つ用意します。場所は apps/<アプリ名>/.worktrees/<機能名>/ です。

ここに落とし穴があって、作業場所の中にも同じ形のフォルダ構造がもう一度現れます。 以前、この二重構造のせいで規則 1・2・3・5・9・10 がまとめて素通りしていたことがありました （受領書なしで「テスト完了」を書き込めてしまった）。 いまは書き込み先のパスを「どの作業場所に属するか」で読み替えてから判定しているので、 どこから書いても同じ規則が同じ意味で効きます。

8. 通過チェックのしくみ ― 機械が決めるか、AI が決めるか

これがこのハーネスの中心です。「何を機械が決め、何を AI に任せているか」を曖昧にしないことを重視しています。

3 つの層

層誰が判定いつすり抜けられるか
① 見張り（12 の規則）機械だけ操作の直前Claude Code を使わない編集ならすり抜ける
② 事後チェック機械だけコマンド実行の直後すり抜けた書き込みを元に戻す（実行自体は止められない）
③ CI（16 項目 A〜Q）機械だけpush したあと①②をすり抜けた分をここで弾く

状態の進み方は 1 段ずつ

未着手 → 契約ドラフト → 契約承認 → 実装中 → 実装完了 → テスト完了 → 統合済み

飛び越しも後退もできません（機械が拒否）。「一時停止」と「差し替え済み」だけは別枠で入れます。 一時停止から戻るときは履歴をさかのぼって直前の状態から判定するので、 「いったん一時停止にしてから好きな状態へ飛ぶ」という抜け道も塞いであります。

いちばん重要な「受領書」の中身

検証スクリプトが実際にコマンドを走らせて、この形の記録を status.yaml に書き込みます。 これは人にも AI にも書けません（書き換えようとすると機械が拒否します）。 

verification_receipt:
  commit: "a1b2c3d..."     ← 検証した時点のコミット。ここが要
  test:
    exit_code: 0           ← 0 以外なら「テスト完了」にできない
    at:        "2026-08-24T10:00:00Z"
    tests:     42          ← テストが 0 件なら「空振り」として拒否
    failures:  0
    skipped:   1           ← 飛ばした割合が多すぎると拒否
  build:     { exit_code: 0, at: ... }   ← 宣言したものだけ検証される
  typecheck: { exit_code: 0, at: ... }
  lint:      { exit_code: 0, at: ... }
  traceability:
    declared: 5            ← 契約で「このテストで確かめる」と宣言した数
    matched:  5
    missing:  []           ← 実在しないテスト名があれば拒否
    failed:   []           ← 失敗しているものがあれば拒否

なぜ「コミット」が要なのか

受領書は「この時点のコードで通った」という主張です。だから受領書に記録されたコミットと、 いまのコミットが一致していなければ「テスト完了」にできません。 これが無いと、実装を書き換えたあとも昔の成功記録を使い回せてしまいます。 push 後の CI では、同じことを別の形（受領書のコミット以降、その機能のフォルダが変わっていないこと）で確認しています。

第三者点検（gate-reviewer）の結果はどう扱うか

AI の判定なので、そのままでは通過の根拠にしません。代わりに次の 3 つで囲っています。

  • 判定は機械的な足し算で決める ― 「重大」が 1 件以上なら NG、0 件なら OK。AI が総合的に「まあ大丈夫でしょう」と言うことはできません
  • 判断基準は 1 つの文書だけ ― review-rubric.md に書かれた軸以外の指摘は無効
  • 書き換える道具を渡さない ― 直すのは実装者の仕事。点検役が自分で直して自分で通す、ができません

記録の形はこうです。件数は数字で書きます（指摘の文章を並べるのは形式違反）。

review:
  verdict: GO          ← GO / NO-GO / ESCALATED（3 回まとまらず人へ）

ただしこの記録は「記録」であって「証明」ではありません。 受領書と違って「実際に実行した」という裏付けが無いからです。だから機械的な通過条件にはしていません。

機械が決めること／AI に任せていること

判定するもの誰が決めるか根拠
どこに書き込んでよいか機械パスとブランチ名の照合
状態を進めてよいか機械状態機械の定義と履歴
テストが通ったか機械実際に実行した終了コードとテスト結果ファイル
機能どうしのつなぎ目が合っているか機械入出力の形式定義どうしを突き合わせる
要件が全部テストで覆われているか機械要件 ID とテスト名の対応表
危険な操作かどうか機械コマンド文字列の解析（規則12）
実装の品質が十分かAI が指摘 → 機械が集計点検基準の文書＋重大件数の足し算
機能の分け方が適切かAI意図的に AI に任せている（機械には判定できない）
要件の内容が正しいか人 ＋ AI要件の承認だけは常に人が必須
承認者が本当に人間か―判定できない。「承認者名と日時が空でないこと」までしか機械化できない

危険な操作の拒否（規則12）

次の 6 つは、他の規則が許していても問答無用で拒否されます。

種別拒否される例通る例
リポジトリの外を消すrm -rf /、rm -rf ../別プロジェクト、rm -rf $変数rm -rf ./build
秘密ファイルを読む.env、*.pem、*.key、SSH や AWS の設定.env.example（見本）
履歴を壊すgit push --force、git reset --hard、git clean -fdxgit push、git revert
検証を飛ばすgit commit --no-verifyふつうの git commit
外部に送るデータを付けた POST、貼り付けサイトへの送信ふつうの読み取りダウンロード
権限を上げるsudo を付けたコマンド―

「これを実行してよいですか？」と AI に確認させる方式は採っていません。 自動で最後まで進めるモードでは AI が自分で「はい」と答えてしまうので、確認は歯止めになりません。 人の判断を挟みたい操作は、拒否したうえで人が自分の手で実行する運用にしています。

9. 気をつけて見たほうがいいところ

Q. 見張りが止めてきたら、回り道を探していい？
いいえ。止まったこと自体が「いまやろうとしていることが工程上おかしい」という信号です。 エラーメッセージに正しい進み方が書いてあるので、そちらに従ってください。
Q. 見張りが「判断できない」ときはどうなる？ ― 通します
これは知っておいたほうがいい性質です。見張りには 2 つの止まり方があり、挙動が逆になります。
  • 壊れたとき（判定の途中でエラー） → 止める。 「判定できなかったのに通す」と、全部の規則が黙って無効になるからです。
  • 判断材料が無いとき → 通す。 たとえば「対応する設定ファイルがまだ無い」「git の情報が取れない」「まだ 1 度もコミットしていない」 といった場合、見張りは判定をあきらめて通します。
つまり「材料を消せば、その規則は発火しなくなる」ということでもあります。 これは見張り単体では塞げないので、push 後の CI 側は逆に「無ければ違反」で判定します （たとえばテスト実行コマンドがどこにも宣言されていないのに「テスト完了」になっていたら、CI が不合格にします）。 実行前の見張りは寛容に、push 後の CI は厳格に、という非対称は意図的な設計です。
Q. すべてのファイル操作に、12 の規則が全部かかる？
いいえ。操作の種類によって効く規則が変わります。 ふつうの読み書き（Edit / Write / MultiEdit）には 12 個すべてが効きます。 それ以外の手段（コマンド実行やノートブック編集）では、書き込んだ後にファイルがどうなるかを 機械が予測できないため、承認・状態遷移・受領書といった「中身を見比べて判定する規則」が働きません。 そこでその 4 つのファイル（状態・要件・設計・統合記録）については、予測できない手段での 書き込みそのものを拒否しています。ファイルを読むだけの操作には、危険操作の規則 （秘密ファイルの読み取り）だけがかかります。

なお、ハーネス自身の検証スクリプトが受領書を書き込む経路は止めません。 止めてしまうと受領書が作れず、永久に「テスト完了」へ進めなくなるためです。
Q. 進捗ダッシュボードを手で直していい？
いけません。PROGRESS.md と STATE.machine.yaml は自動生成です。 手で直しても次の更新で消えますし、push 後の CI が「中身と一致していない」として弾きます。
Q. ダッシュボードのどこを見れば状況がわかる？
先頭に「自動化モード」「要件・設計の承認状況」「見張りの状態」「ハーネスの版」が出ます。 見張りの状態が「異常」なら、その会話では機械の強制が効いていない可能性があります。 --html を付ければ、非エンジニア向けの画面も出せます。
Q. 「テスト完了」にできない、と言われたら？
だいたい原因は 3 つのどれかです。①受領書が無い ②検証したあとにコードを変えた ③宣言したテスト名が実在しない。いちばん多いのは②で、受領書を作ったあとに うっかり先にコミットして、記録と現状がずれるパターンです。
Q. ハーネス自体を直したいときは？
harness/<内容> という名前のブランチを作ってください。それ以外のブランチでは書き込めません。 直したら CHANGELOG.md への追記も必須です（忘れると CI が落ちます）。
Q. 規約に新しい節を足したい
できません。15 節で凍結されています。既存の節の中に足してください。 どうしても新設が必要なら、人の明示的な許可を取ってから凍結の設定を変える必要があります。

11. この案内書は何を見て書かれているか

説明書が実物とずれていると、読んだ人が間違った前提で動いてしまいます。そこでこの案内書は、 実際に動くもの（プログラム・設定ファイル・AI への指示書）だけを見て書いています。 「人が読むために書かれた説明文」は、更新が追いついていない可能性があるので出典にしていません。

書いてあることどこから取ったか
見張りが動くタイミング・制限時間Claude Code が実際に読む設定ファイル .claude/settings.json
push 後のチェック 16 項目チェックプログラムが実際に呼び出している関数（説明コメントではなく）

照合してわかったこと

説明文と実物のあいだに食い違いは見つかりませんでした。ただし実物にしか書かれていない性質が 2 つあり、どちらもこの版で追記しました ― ①見張りが「判断材料が無い」ときは通すこと ②操作の種類によって効く規則が変わること。 そして②を調べる過程で、実際に 3 つの抜け道が見つかったので塞ぎました （ノートブック編集で「テスト完了」にできた／コマンド実行とノートブック編集で統合の受領書を 手書きできた）。 （どちらも「9. 気をつけて見たほうがいいところ」にあります）
