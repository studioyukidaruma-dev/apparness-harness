# apparness 改修方針（人間向け）

作成日: 2026-08-24
根拠: `docs/archive/harness-comparison-technical.html` / `docs/archive/harness-comparison-plain.html`（apparness v1 と claude-code-harness v5.11.0 の比較）
機械向けの対応ファイル: [`docs/plans/IMPROVEMENT-PLAN.machine.yaml`](IMPROVEMENT-PLAN.machine.yaml)

> **この文書の役割**
> 「なぜその改修をするのか」を人間が判断するための文書です。
> 実際に AI に改修させるときは `docs/plans/IMPROVEMENT-PLAN.machine.yaml` を読ませてください。
> 内容は 1 対 1 で対応しています（タスク ID が同じ）。

---

## 1. 比較の結論を一段落で

claude-code-harness は 5 世代作り直された完成品で、危険操作の遮断・マルチホスト・配布・
非エンジニア向け画面・リリース自動化まで揃っています。**総合力では明らかに向こうが上です。**
しかし apparness には向こうが持っていない芯があります——
**「AI がテストを通したと嘘をつけない」「要件を変えたのに設計が古いまま先に進めない」
「並行して作った機能どうしのつなぎ目が食い違ったら止まる」** という、
実行結果そのものを機械が検証するゲートです。
向こうの同等機構は自己申告ベースで、しかも配布既定では無効になっています。

**したがって改修方針は「追いつく」ではなく「芯を守りながら、向こうが押さえている脅威だけを埋める」です。**

## 2. いちばん先に知っておくべき制約

### 2-1. いま、規約に 1 行も追記できません

| ファイル | 現在 | 上限 | 残り |
|---|---:|---:|---:|
| `harness/CONVENTIONS.md` | 35,891 B | 36,000 B | **109 B** |
| `.claude/agents/feature-builder.md` | 11,981 B | 12,000 B | **19 B** |
| `.claude/agents/solution-architect.md` | 11,352 B | 12,000 B | 648 B |
| `.claude/agents/integrator.md` | 8,224 B | 12,000 B | 3,776 B |
| `.claude/agents/gate-reviewer.md` | 4,907 B | 12,000 B | 7,093 B |
| `.claude/agents/requirements-analyst.md` | 4,164 B | 12,000 B | 7,836 B |

CI 項目 L がこの上限を機械的に強制しています。
さらに項目 O が `CONVENTIONS.md` を 15 節で凍結していて、16 節目を作ろうとすると落ちます。

つまり **「Rule を 1 本足す」という最も自然な改修が、いまは実行できません。**
これは不具合ではなく、設計どおりに肥大化防止が働いている状態です。
**改修の 1 番目の作業は機能追加ではなく、説明文を `docs/HARNESS_GUIDE.md` に引っ越して場所を空けること（T-001）になります。**

なお引っ越すときは **移設であって複製にしない** でください。
両方に残すと今度は項目 M（二重管理の検出）が落ちます。

### 2-2. 作業ブランチが要ります

`harness/**`・`.claude/**`・`.github/**` への書き込みは Rule 1 で保護されているため、
着手前に `git switch -c harness/<topic>` してください。
`HARNESS_UNLOCK=1` は緊急避難路なので、この改修では使わないでください。

## 3. 絶対に壊してはいけないもの（7 項目）

改修案がどれだけ良く見えても、次を壊すなら却下してください。

1. **AI の自己申告を根拠にしたゲートを新設しない。** これが apparness の差別化のすべてです。
2. **検証受領書を手書きできるようにしない。** 手書きできた時点で Rule 10 は意味を失います。
3. **受領書の commit と HEAD の一致条件を緩めない。** これが無いと過去の成功記録を使い回せます。
4. **Bash 検知に解除用の環境変数を足さない。** AI が自分で解除できたら決定論ではありません。
5. **Hook を標準ライブラリだけで動く状態に保つ。** 全部読めることが比較対象に対する優位です。
6. **gate-reviewer の verdict は深刻度の機械集計のままにする。** レビューアに Write/Edit も与えない。
7. **スタック固有の標準をハーネス本体に書かない。** アプリ非依存性の根幹です。

## 4. 改修の中身

### フェーズ 0 — 土台（これをやらないと他が着手できない）

#### T-001 コンテキスト予算の再配分 🔴 最優先

**なぜ**: 上記 2-1 のとおり満杯だから。他のすべての文書追加タスクがこれを待っています。

**やること**: `CONVENTIONS.md` から「設計意図・背景・経緯」を `docs/HARNESS_GUIDE.md` に移し、
規範の一文と節番号だけを残す。移設候補の筆頭は 7 節の各 Rule に付いている経緯説明、
7 節末尾の worktree 読み替えと二段検知の解説、12 節の設計意図、15 節の背景です。
`feature-builder.md` はフェーズ固有の長い手順を `harness/procedures/feature-build.md`
（オンデマンド読み込み＝予算対象外）に切り出します。

**完了の目安**: 規約 29,000 B 以下、feature-builder 10,000 B 以下、節数は 15 のまま。

---

#### T-002 「規則」と「それが本当に効いていることを示すテスト」の対応表

**なぜ**: F-029/F-030 では、Rule 1・2・3・5・9・10 が **6 本まとめて空振りしていた**のに、
それに気付ける経路がありませんでした。静的検知も事後検証も、どちらもその経路では動いていませんでした。

比較対象には `docs/claims-audit.md` という「主張を、いま証明済みか / 追加証拠が要るか で仕分けた表」があり、
自社の目玉機能を自分で「まだ強く主張するのは安全でない」と格下げしています。
この規律を apparness では「規則 ↔ 実証テスト」の対応として実装します。

**やること**: `harness/CLAIMS.md` を作り、Rule 1〜11 と CI 項目 A〜O のそれぞれについて
「何をブロックすると主張するか / それを実証するテスト名 / 最終実証日 / 未実証の残余」を表にする。
足りないテストを書く。とくに worktree 経由の経路は、worktree の内と外の両方から検証する。
表に書いたテスト名が実在するかを CI で検証して、表と実体のズレを防ぐ。

---

### フェーズ 1 — 安全性の穴を塞ぐ

#### T-010 Rule 12: 危険操作フロアの新設 🔴 最重要

**なぜ**: 調べたところ、**apparness の Hook 11 ルールのうち、危険操作を防ぐものは 0 件**でした。
次のことが全部素通りします。

| AI がやってしまうと困ること | apparness | claude-code-harness |
|---|---|---|
| リポジトリ外のフォルダを再帰削除 | 止まらない | 止まる |
| `.env` や秘密鍵を読む | 止まらない | 止まる |
| 読んだ内容を外部に送信する | 止まらない | 止まる |
| force push・履歴の巻き戻し | 止まらない | 止まる |
| `--no-verify` で検証を飛ばしてコミット | 止まらない | 止まる |
| `sudo` を伴うコマンド | 止まらない | 止まる |

これは設計範囲の外だったので「手抜き」ではありませんが、
**AUTONOMOUS モードで長時間走らせる前提のハーネスとしては、いちばん重い穴です。**

**やること**: `pre_tool_use_guard.py` に Rule 12 を追加する。7 節への追記なので項目 O は通ります。
遮断対象は D-1〜D-6 の 6 分類（machine.yaml 参照）。
既存の `extract_bash_candidate_paths` を再利用し、新しいパーサは増やさない。
**バイパス用の環境変数は用意しない**（不変条件 4）。

**設計上の判断で 1 つ強調しておきたいこと**:
比較対象は危険操作の一部を「人に確認する（ask）」で処理していますが、
**apparness では ask ではなく deny にしてください。**
AUTONOMOUS モードでは AI 自身が確認に答えてしまうので、ask は実質的な素通りになります。
人間の判断を挟みたい操作は、拒否したうえで「人間が別途手で実行する」運用に倒すのが確実です。

---

#### T-011 強制レイヤ自身が生きているかの確認

**なぜ**: これは両方のハーネスに共通する、いちばん見落とされやすい穴です。

`python3` が PATH に無い、import に失敗する、タイムアウトする——
このいずれでも Hook は「ブロックしない」終了コードで終わり、
Claude Code はそれを **「判断なし＝通過」** として扱います。
つまり **11 個の見張り番が全部消えた状態で、何事もなかったように作業が続きます。**

比較対象も同じです。起動 shim はバイナリが見つからないと stderr に診断を出して
**exit 0・標準出力なし**で終わります。「絶対に外せない実行時フロア」という説明は、
バイナリが実在して実行可能であることを前提にした話です。

**やること**: SessionStart フックで健全性を検査し、
失敗したら「このセッションでは決定論的強制が効いていない」ことをはっきり出す。
`PROGRESS.md` の先頭に「強制レイヤの状態」行を出す。
PreToolUse 本体は、想定外の例外を握りつぶさず **拒否（fail-closed）** に倒す。

### フェーズ 2 — 既知の不具合と追跡可能性

#### T-020 Bash 静的検知のヒアドキュメント誤検知

**なぜ**: この比較報告書を書いている最中に実際に踏みました。
リポジトリルート直下に HTML を heredoc で書き出そうとしたところ、
**HTML の本文中に現れた `harness/hooks/...` という文字列**をコマンド引数と誤認して Rule 1 が発火しました。

安全側の誤りですし、構造化ツール（Write）に切り替えれば回避できるので、
規約が意図した回避経路どおりに動いてはいます。
ただし規約 7 節は「誤検知を見つけたら検知ロジック自体を修正する」と定めているので、対象になります。

**注意**: これは検知を**緩める**方向の変更です。
ヒアドキュメントの「本文」だけを除外し、「リダイレクト先」は従来どおり検知対象に残してください。
引用符で囲まれた文字列を一律に除外すると、`cp "harness/x" y` が素通りします。

---

#### T-021 版管理の導入（VERSION / CHANGELOG）

**なぜ**: いま `VERSION` も `CHANGELOG.md` も無く、git 履歴は 1 コミットに潰れています。
どの版のハーネスが動いているのかを機械的に特定できないので、
不具合報告と改修の対応が取れません。

---

#### T-022 ドッグフーディング成果物の保全

**なぜ**: 3 アプリ（md-todo-cli / bookmark-vault / habit-tui）を `INTEGRATED` まで完走した、
というのが apparness のいちばん重要な実績ですが、
`apps/` が存在せず git 履歴も潰れているため、**第三者が——そして半年後の自分が——追検証できません。**

全部をこのリポジトリに戻す必要はありません。
「どこに何が残っていて、そこで何を確認できるか」が `docs/maintenance/DOGFOODING-LOG.md` から辿れれば十分です。
あわせて、未着手のまま残っている F-059 / F-060 / F-064 を記録の先頭付近に明示してください。

---

### フェーズ 3 — 運用面の底上げ

#### T-030 非エンジニア向け HTML 面

比較対象は「計画概要 / 進捗 / 受け入れ」の HTML 3 面を持っていて、これは分かりやすい優位です。
ただし **skill を 3 つ増やすのは真似しないでください**（後述の「やらないこと」参照）。
apparness には `render_progress.py` という決定論的レンダラが既にあるので、
`--html` オプションを足すだけで実現できます。
入力は `STATE.machine.yaml` と `status.yaml` だけにして、AI に作文させないこと。
生成物は `.gitignore` に入れます（派生物を判断の根拠にしない、という比較対象の原則は正しい）。

#### T-031 既知の制約の記録形式を統一

比較対象の `known-limitations.md` は **症状 / 根本原因 / 適用中の緩和策 / 再検討の条件** の
4 点セットで統一されていて、とくに「いつ再検討するか」が全項目に書いてあるのが優れています。
`docs/HARNESS_GUIDE.md` 11 節をこの形式に揃え、
「apparness 側で直せるもの」に分類された項目はタスクに昇格させてください。

#### T-032 摩擦点から再発防止テストへの変換を手順化

77 件の摩擦点は貴重な資産ですが、テストへの変換が場当たりになっています。
**深刻度 最高・高 の摩擦点は、テスト無しでクローズしない**というルールにするのが要点です。

## 5. やらないこと（重要）

これは「まだやらない」ではなく「意識的にやらない」リストです。
比較対象が持っているからといって取り込むと、apparness の価値を損ないます。

| やらないこと | 理由 |
|---|---|
| **マルチホスト対応**（Codex / Cursor / Grok） | apparness の Rule 3・7・9・10・11 は「書き込み前後の内容比較」に依存する。Bash-only の hook しか持たないホストでは**原理的に成立しない**。比較対象自身が「同じ機能名でも守りの強さは違う」と明記して false parity を禁じている。同じ罠に入らない |
| **強制エンジンの Go 化・バイナリ配布** | 比較対象は 13 MB の Go バイナリのみを配布し、**その元になったソースが配布物に 1 ファイルも入っていなかった**（実測）。AI を縛る側のコードが全部読めることは apparness の明確な優位で、性能のために手放す価値はない。性能が問題になったら、まず Hook の発火回数と matcher の絞り込みで対処する |
| **skill / subagent / ドキュメントの数を増やす** | 比較対象は skill 23・スクリプト 155・docs 143 に達し、**認知負荷そのものを扱う文書**を持つに至っている。apparness の CI 項目 L / M / O はまさにこれを防ぐ装置。新機能は既存の script のオプションとして実装するのを第一候補にする |
| **既存リポジトリでの日常開発（brownfield）対応** | `apps/<app-id>` の構造と状態機械が前提になっており、対応は事実上の作り直し。その用途には claude-code-harness を併用するほうが合理的。**スコープ外であることを `docs/HARNESS_GUIDE.md` に明記する**のが誠実 |
| **検証ゲートを「既定オフ」にできる設定** | 比較対象は TDD 強制を配布既定で無効にしている（`enabled = false`）。強制機構が存在しても効いていない状態が既定、というのは避ける。apparness の Rule 10 / 11 は既定で常に効く。この性質を設定可能にしない |
| **危険操作を deny ではなく ask にする** | AUTONOMOUS モードでは AI が自分で確認に答えてしまう |

## 6. 進め方のまとめ

```
フェーズ 0（土台）      T-000 ブランチ作成
                        T-001 コンテキスト予算の再配分   ← ここを飛ばすと全部 CI で落ちる
                        T-002 規則 ↔ 実証テストの対応表

フェーズ 1（安全）      T-010 Rule 12 危険操作フロア     ← 実運用でいちばん重い穴
                        T-011 強制レイヤの健全性自己診断

フェーズ 2（不具合）    T-020 heredoc 誤検知の修正
                        T-021 VERSION / CHANGELOG
                        T-022 ドッグフーディング成果物の保全

フェーズ 3（運用）      T-030 非エンジニア向け HTML
                        T-031 既知の制約の形式統一
                        T-032 摩擦点 → 再発防止テスト
```

各タスクの完了時は、必ずこの 3 つを実行して緑を確認してください。

```bash
python3 -m pytest harness/tests -q
python3 harness/scripts/ci_check.py --branch "$(git branch --show-current)"
wc -c harness/CONVENTIONS.md .claude/agents/*.md   # 予算の余裕を確認
```

## 7. 最後に — この改修で守るべき一線

比較して分かったのは、**apparness の弱さは「小さいこと」ではない**ということです。
12,398 行で、87,547 行の相手が持っていない強制機構を成立させています。

危険なのは、機能数やドキュメント量で追いつこうとして、
**項目 L / M / O という自分の防波堤を緩めてしまうこと**です。
比較対象はその規模ゆえに、認知負荷を管理するための文書を書く段階に来ています。

**取り込むべきは相手の機能ではなく、相手が押さえている脅威です。**
それは危険操作の遮断（T-010）と、見張り番自身が生きているかの確認（T-011）の 2 つだけ。
残りは apparness 自身の弱点（予算・追跡可能性・実証）を潰す作業です。
