## AI に改修させるとき

Claude Code のセッションをこのリポジトリのルートで開いて、こう頼めば動きます。

```
docs/plans/REPAIR-ORDER.machine.yaml を読んで、priority 順に改修してください。
```

特定の項目だけやらせたいときは ID で指定します。

```
docs/plans/REPAIR-ORDER.machine.yaml の R-010 と R-011 だけ実施してください。
```

機械可読側の `how_to_use` に手順が、`obligations` に「これをやらないと CI が落ちる」義務が、
`global_verification` に最後に必ず実行させるコマンドが入っています。
`final_report_to_user` で「検証コマンドを実行せずに完了と報告すること」を明示的に禁じています。

> **最初に必ず R-000（ブランチ作成）が実行されます。**
> このハーネスは Rule 1 で `harness/` `.claude/` `.github/` への書き込みを保護しており、
> `harness/<topic>` ブランチでなければ AI 自身が書き込めません。改修指示書がその制約に従う形になっています。

## まず、壊れていないことの確認

改修の話をする前に、実測で**主張どおり動いた**部分を挙げておきます。ここは触りません。

- 自己テスト **656 件すべて成功**（15.12 秒）、`ci_check.py` も `exit 0`
- Rule 1・2・7・9・10・11 はいずれも宣言どおり拒否
- Rule 12（危険操作）は D-1〜D-6 すべて拒否。`rm -fr` / `rm -r -f` / `rm -Rf` / `../..` / `$HOME` の
  綴り変えも捕捉。無害な `curl` の GET や `pytest` は通す（誤検知なし）
- **二段防御が実際に機能した。** 変数展開や `bash -c` に隠した書き込み・削除は事前チェックを
  すり抜けますが、実行後の `git status` 差分が検知して**ファイルを復元しました**
- 受領書チェーンが全経路で動作。テスト失敗時は `exit_code: 1` を正直に記録して昇格を拒否し、
  実装を 1 コミット進めると受領書が HEAD 不一致で無効化されました
- CI の 3 ジョブは `needs` 無しの独立実行。片方の失敗が他方を隠す構造になっていません

つまり**中核は健全**です。以下は周辺の穴です。

## 改修項目

優先度順。工数は目安です。

### 優先度 1 — 強制レイヤが黙って壊れる経路を塞ぐ

#### R-010 · hook 入力が壊れていると素通りする

`pre_tool_use_guard.py` は「判定できないなら通すのではなく止める」と宣言し、その理由まで
コード内に書いています。ところが**入力そのものが壊れている場合には効きません**。

```
$ echo 'not json' | python3 harness/hooks/pre_tool_use_guard.py
exit=0        ← 止まらない
```

原因は `read_hook_input()` が JSON の解析エラーを空辞書に潰していることです。空辞書だと
ツール名が無いので「判定対象外」として通ります。宣言と実装の範囲がずれている状態です。

実運用では Claude Code が常に正しい JSON を渡すので実害は出ていません。ただし
**宣言している安全性の範囲が実際より広く見える**のは、このハーネスの性格上いちばん避けたい種類の
ずれです。

対応は範囲を絞ります。「中身があるのに JSON として読めない」場合だけ拒否し、
**空入力は通したまま**にします（ホストが payload 無しでイベントを呼ぶ経路を止めると通常運用が壊れる）。
適用先もブロックする hook だけで、非ブロッキングの Rule 4 側は現状維持です。

工数: 小（1〜2 時間）／ リスク: 低

#### R-011 · git リポジトリ外だと強制が全面的に沈黙する

判定はすべて git 情報に依存していて、取れない場合は「判定不能」として通します。
誤爆でユーザーの作業を壊さないための設計判断で、これ自体は妥当です。

問題は**それが見えないこと**です。

```
$ cd /tmp/nogit && echo '{}' | python3 .../session_start_healthcheck.py
（出力なし）exit=0
```

強制レイヤが丸ごと効いていない状態で、何も言わずに作業が始まります。過去の F-029 / F-030
（中核 Rule 群が一斉に空振りしていたのに誰も気付けなかった）と同じ形の失敗です。

対応は**可視化だけ**です。SessionStart の健全性診断に「このセッションでは Rule 1 / 2 / 6 が
判定不能です」と言わせます。強制を追加するわけではないので、`exit 0` は維持します。

工数: 小（1〜2 時間）／ リスク: 低

---

### 優先度 2 — 運用の詰まりと、説明文のずれ

#### R-020 · 脆弱性走査に逃げ道が無い

`vuln_scan.py` に抑制の仕組みが一切ありません。上流に修正が出ていない脆弱性を 1 件踏むと、
そのアプリは CI を通せなくなります。

逃げ道が無いと、現場は最終的に**ジョブごと外す**方向に倒れます。検査が形骸化するのがいちばん悪い
結末です。

ここは KSD の設計をそのまま借りるのが良いです。KSD は見逃し許可を 1 行 1 件で書かせ、
`expires=` と `reason=` の両方を必須にし、**欠落や期限切れがあればその時点で CI を落とします**。
「とりあえず無視」の永久化を機械で防ぐ形です。しかもこの設計はスタックに依存しないので、
apparness の「スタック固有の標準を本体に規定しない」という不変条件に抵触しません。

置き場所は `apps/<app-id>/.vuln-ignore`（ハーネス本体ではなくアプリ側の受容判断なので）。
抑制ファイルが無ければ挙動は完全に従来どおり、という後方互換を条件にしています。

工数: 中（半日）／ リスク: 低

#### R-021 · 雛形生成が生のエラーを吐く

git の `user.email` が未設定の環境で `new_feature_scaffold.py` を動かすと、Python の
`CalledProcessError` の traceback がそのまま出ます。

このリポジトリの他のスクリプトは全部 `エラー: …` + 次の一手、という様式を守っているので、
ここだけが例外です。失敗が「ハーネスのバグ」に見えて、実際の原因（環境側の設定）に
到達できません。

工数: 小（1 時間）／ リスク: 低

#### R-022 · 説明文が実体と違う

`pre_tool_use_guard.py` の冒頭に「**バイパス用の環境変数は意図的に用意しない**」と書かれて
いますが、Rule 1 には `HARNESS_UNLOCK=1` があります。

これは書き方の問題です。その文はもともと Bash 間接書き込み検知について書かれたもので、
`CLAIMS.md` 側は Rule 1 の行に「意図的な緊急避難路」として `HARNESS_UNLOCK` を明記しています。
**対応表は正確で、誤っているのは説明文だけ**なので、直す対象もそこだけです。強制の実体は変えません。

工数: 極小（15 分）／ リスク: なし

### 優先度 3 — 任意

#### R-030 · 存在しない状態名が手元で止まらない（任意）

`state: IMPLEMENTING` のような架空の状態名を書くと、hook は通して CI の形式チェックで初めて
落ちます。

**これはバグではありません。** コード内に「未知の値の妥当性は JSON Schema 側の責務」と明示
されており、意図的な責務分担です。正しさの問題ではなく、フィードバックが遅い問題です。

着手するなら、状態の一覧が hook 側と JSON Schema 側で**二重管理にならないこと**が条件です。
食い違うと hook と CI の判定がずれて、いま以上に悪くなります。

工数: 中（半日）／ リスク: 中（二重管理を作ると悪化する）

#### R-031 · デリバリー層が無いことを「決めたこと」として書く

apparness にはデプロイ・Terraform・コンテナ検査・secret 管理が一切ありません。KSD との比較では
一方的な負けです。

**ただしこれは埋めるべき欠陥ではありません。** 本体に CD を持ち込むと「スタック固有の標準を
本体に規定しない」という不変条件に正面から抵触し、apparness の同一性そのものが変わります。

移植すべきは成果物ではなく、スタックに依存しないパターンだけ（それが R-020 です）。
残りは `docs/HARNESS_GUIDE.md` に**意図的な非スコープとして明記する**のが正しい対応です。
これを書かないと、比較レポートを読んだ人が CD の実装を提案し続けることになります。

工数: 小（1〜2 時間・文書のみ）／ リスク: なし

## 着手しないもの

指示書には**やらない理由つきで**入れてあります。AI が善意で手を出さないようにするためです。

### R-DEFER-1 · 読み取りと外部送信の事後検知

静的検知は `bash -c` のような包み方をすり抜けます。ただし**書き込みと削除は事後検証が捕まえて
復元することを実測で確認しました**。

```
$ bash -c "rm harness/CONVENTIONS.md"     # 事前チェックは通過
$ post_tool_use_guard.py                  # → 検知して復元、exit 2
restored? YES
```

残る穴は「作業ツリーを変えない操作」＝秘密ファイルの読み取りと外部送信だけです。
そしてこれは既存プランの **T-040 と同じ穴**で、あちらが「実地で 1 件でもすり抜けが観測される
まで着手しない」という条件を明示しています。予防的に着手すると、検知手段（プロセス監視・
ネットワーク監視）が「標準ライブラリのみ」という不変条件と衝突します。

その判断を維持します。すり抜けを観測したら `docs/maintenance/DOGFOODING-LOG.md` に記録して T-040 を起動する、
という運びです。

### R-DEFER-2 · main ブランチでのハーネス不変チェック

CI のハーネス保護チェックは既定ブランチでは動きません。fast-forward マージ運用では
「元々どのブランチのコミットか」が git 上に残らないため、`main` への直接押し込みと正当な
`harness/<topic>` のマージが区別できないからです（理由はコード内に明記されています）。

有効化すると正当なマージが必ず落ちます。回避にはマージコミットの強制などの運用変更が必要で、
これは改修ではなく**運用方針の決定**です。ユーザーが決めることなので、AI には提案までに
留めさせます。

## 全体の検証

改修後、AI には必ずこれを実行させてください（指示書の `global_verification` に入っています）。

```bash
python3 -m pytest harness/tests -q                                  # 656 件以上が緑
python3 harness/scripts/ci_check.py --branch $(git branch --show-current)
python3 harness/scripts/vuln_scan.py
wc -c harness/CONVENTIONS.md .claude/agents/*.md                    # 予算の余裕を確認
git log --oneline -1 -- CHANGELOG.md                                # 追記されているか
```

### AI が忘れやすい義務

このハーネスは改修者にも機械的な要求をかけてきます。指示書の `obligations` に入れてありますが、
人間側も知っておくと事故が減ります。

| | 要求 | 落ちる場所 |
|---|---|---|
| OB-1 | `harness/` `.claude/` `.github/` を触ったら `CHANGELOG.md` の `[Unreleased]` に項目を追記 | CI 項目 Q |
| OB-2 | ブロック挙動を変えたら `CLAIMS.md` に行を足し、**実在するテスト**を書く | CI 項目 P |
| OB-3 | 判定ロジックを変える前後で `harness/tests` を緑に保つ | CI / 運用規約 |
| OB-4 | `harness/hooks/**` に外部ライブラリを import しない | 設計不変条件 |

そしてもう 2 つ、機械が強制する制約があります。

- **`CONVENTIONS.md` は 15 節で凍結**されています。新しい節は作れません。既存の節に統合させてください。
- **`CONVENTIONS.md` と agent プロンプトに同じ文章を二重に書くと CI が落ちます**（重複検出）。
  解説は `docs/HARNESS_GUIDE.md` へ、規範だけ `CONVENTIONS.md` へ、という分担です。
  なお `.claude/agents/solution-architect.md` は残り 648 バイトしかありません。ここへの追記は
  1 行でも危険です。

## この指示書について

すべての発見は実行由来です。コードを読んで「こう見える」ではなく、走らせて終了コードと
出力を確認しています。実測値・実行結果は機械可読側の `measured_state` に、
根拠となった観測は `findings` の `evidence` に入れてあります。

なお、本指示書を書く際には既存の `docs/plans/IMPROVEMENT-PLAN.machine.yaml` を読んでいます。
比較レポートの結論を出すときには人間向け散文を除外しましたが、こちらは**重複した提案を出さない**
ために必要な参照です（実際、私が挙げようとした 1 項目は既存の T-040 と同じ穴でした）。
参照したのは既存プランの構造・不変条件・やらないこと・タスク一覧で、
その主張を証拠として採用してはいません。
