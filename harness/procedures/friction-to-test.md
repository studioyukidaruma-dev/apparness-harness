# friction-to-test.md — 摩擦点を再発防止テストへ変換する手順（オンデマンド読み込み）

`DOGFOODING-LOG.md` に溜まった摩擦点（F-xxx）を、再発を検出するテストへ変換するための手順。
コンテキスト予算（`CONVENTIONS.md` 15節）の対象外。ハーネスを保守する人間と、その改修を
担当するセッションが読む。

## なぜこの手順が要るか

摩擦点はこのハーネスが**実地で壊れた記録**であり、いちばん価値の高い入力である。
ところがテストへの変換が場当たりだった。実際、F-029/F-030 では中核ルール群（Rule 1・2・3・5・
9・10）が丸ごと空振りしていたのに、17 ファイル 3,800 行のテストがありながら誰も気付けなかった。
**テストが無いまま「改修済み」と書いた摩擦点は、いつ再発しても分からない。**

## ルール

**深刻度が「最高」または「高」の摩擦点は、再発を検出するテストが無い状態でクローズしない。**

テストが書けないものは、`harness/CLAIMS.md` の「深刻度 最高・高 の摩擦点 → 再発防止テスト」の表で
**「未実証の残余」列になぜ書けないかを書く**。空欄は CI 項目 P が拒否する。
中・低の摩擦点はこの表の対象外（テストを書いてもよいが、必須ではない）。

## 手順

1. **摩擦点の深刻度を確認する。** 最高・高でなければ、この手順の対象外（記録のみでよい）。
2. **「何が起きたか」を 1 文に落とす。** 原因ではなく**観測できた事象**で書く
   （例:「受領書なしで `state: TESTED` を書き込めた」）。これがテストの assert になる。
3. **その事象を再現する最小の入力を作る。** 既存のテストのフィクスチャを流用する:
   - Hook の end-to-end → `test_pre_tool_use_guard.py` / `test_rule_coverage.py`
   - worktree 経由の経路 → `test_worktree_scope.py` / `test_rule_coverage.py`
   - Bash の事後検証 → `test_post_tool_use_guard.py`
   - CI 項目 → `test_ci_items.py`
   - 判定ロジック単体 → `test_path_utils_*.py` / `test_verification.py` / `test_traceability.py`
   - 過去の摩擦点の回帰 → `test_dogfooding_fixes.py`
4. **「拒否される」と「正当なケースが通る」を対で書く。** 片方だけだと、締めすぎ／緩めすぎの
   どちらかに倒れたときに気付けない。とくに**緩める方向の改修**では後者が要る。
5. **改修の前にテストを書き、落ちることを確認する**（`CONVENTIONS.md` の selftest-first）。
   落ちないテストは、その摩擦点を再現できていない。
6. **`harness/CLAIMS.md` の表に行を足す。** 列は
   `摩擦点 / 何が起きたか / 再発防止テスト / 最終実証日 / 未実証の残余`。
   テスト名は `<ファイル名>::<テスト関数名>` で書く（CI 項目 P が実在を検証する）。
7. **`DOGFOODING-LOG.md` の該当項目に「→ 改修済み（日付）」と、対応テストへの参照を書く。**
8. `python3 -m pytest harness/tests -q` と
   `python3 harness/scripts/ci_check.py --branch $(git branch --show-current)` を通す。

## 「テスト不要」と書いてよい場合

次のいずれかに当てはまるときだけ。**「面倒だから」「再現が難しいから」は理由にならない。**

- **根本原因がハーネスの制御外にある**（Claude Code のセッション管理・ツール受け渡し・cwd 追跡など）。
  ハーネスから観測も再現もできない。例: F-004・F-031・F-063・F-080。
- **意味論的な判定で、機械には原理的に判定できない**。例: F-010（承認者が本当に人間か）。
  この場合でも、**機械的に固定できる範囲まではテストを書く**（例: 承認記録を伴わない APPROVED の拒否）。
- **手順の問題であり、コードの状態としては表現できない**。例: F-033（受領書とコミットの順序）。
  この場合も、順序を間違えたときに各ルールが期待どおり拒否することはテストする。

いずれの場合も、`CLAIMS.md` の「未実証の残余」列に**その理由と、代わりに何で担保しているか**を書く。

## CI 項目にするかどうか（検討の記録・2026-08-24）

「深刻度 最高・高 の摩擦点にテストが紐づいているか」を CI で機械判定するには、
`DOGFOODING-LOG.md`（140KB の散文）を機械可読にする必要がある。**それは過剰と判断した。**

代わりに、**対応表を `harness/CLAIMS.md` に置いた**。CLAIMS.md は既に CI 項目 P が
「書かれたテスト名が実在するか」「実証テストが無い行に理由があるか」を検証しているので、
新しい CI 項目も新しい機械可読ファイルも増やさずに、表と実体の drift だけは機械的に塞げる。

**残る手作業は「表に行を足し忘れること」の検出だけ**で、これは摩擦点を新規に起票する人間の
判断に依存する（規則の追加そのものが人間の判断であるのと同じ。CLAIMS.md の項目 P の
「未実証の残余」に明記してある）。
