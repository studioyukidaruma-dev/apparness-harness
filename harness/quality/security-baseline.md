# セキュリティ・ベースライン

`feature-builder` が実装するとき、`solution-architect` が技術スタックを選ぶとき、`integrator` が
結線するときに読む。外部Skill（`security-review` 等）の有無に関わらず常に守る最低ラインであり、
find-skills 等で見つかる専門的なルール集は、これに**追加**するものであってこれの代わりにはならない。

網羅的なチェックリストではなく、実装を間違えやすい・見落としやすい項目に絞っている。各項目は
「何をするか」を命令形で書く。抽象的な注意喚起（「気をつける」等）ではなく、実際に手を動かせる
指示にする。

## 1. 外部からの入力は信頼しない

- ユーザー入力・他機能からの入力（`contract.yaml` の `inputs[]`）・外部APIの応答・ファイル内容は、
  すべて「悪意または誤りを含みうるもの」として扱う。
- `contract.yaml` の `inputs[]` に書かれた `json_schema` で型・範囲・必須項目を実装の入口で検証する。
  検証を通らない入力は `error_cases[]` に従って拒否し、処理を先に進めない。
- HTML/Markdown等をそのまま画面に出力しない。テンプレートエンジンやフレームワークの標準エスケープ
  機構を使う（`innerHTML` への直接代入、`dangerouslySetInnerHTML` 等の生埋め込みは避ける）。

## 2. インジェクションを構造的に防ぐ

- SQL・シェルコマンド・NoSQLクエリを文字列結合で組み立てない。パラメータ化クエリ／プリペアド
  ステートメント／ORMの標準APIを使う。
- OSコマンドを実行する場合、ユーザー由来の値をコマンド文字列に直接埋め込まない
  （配列引数渡し等、シェル解釈を経ない方式を使う）。

## 3. 秘密情報をコードに書かない

- APIキー・パスワード・トークン・接続文字列をソースコードやテストコードに直接書かない。
  環境変数または `shared-kernel.yaml` に記述された方針に従った秘密情報管理の仕組みを使う。
- ログ・エラーメッセージ・コミットメッセージに秘密情報や個人情報を出力しない。

## 4. 権限チェックはサーバー側（処理の起点）で行う

- 「この操作をしてよいか」の判定は、UI上の表示/非表示だけに頼らない。実際に処理を行う関数の
  入口で権限チェックを行う。
- 他人のデータを参照・変更するAPI/関数は、要求元が対象データの所有者・権限者であることを
  処理の中で確認してから実行する。

## 5. エラー処理は内部情報を漏らさない

- ユーザーに見せるエラーメッセージに、スタックトレース・内部パス・DBスキーマ・使用ライブラリの
  詳細を含めない。`contract.yaml` の `error_cases[]` に定義した形にとどめる。
- 例外を握りつぶして処理を継続しない。捕捉したら `error_cases[]` に沿って明示的に応答する。

## 6. 依存ライブラリは選定時に確認する

- 新しい依存を追加する前に、既知の脆弱性・最終更新日・メンテナ体制を確認する
  （`solution-architect` が設計時に行うのが基本だが、`feature-builder` が実装中に新規追加する
  場合も同様に確認し、`contract.yaml` の `tech_stack.libraries[].notes` に確認結果を記録する）。
- 長期未更新・非推奨・脆弱性報告のあるライブラリは避ける。
- ここでの確認は選定時点の一度きりの人間/AI判断だが、`apps/` 配下の lockfile は CI
  （`.github/workflows/harness-checks.yml` の `vuln-scan` job、`harness/scripts/vuln_scan.py`）
  で push・PRのたびに OSV-Scanner による機械的な再検証を受ける。新たに公表された脆弱性も
  以後の push で検知されるため、選定時に見落とした・後から報告された脆弱性の safety net になる。
