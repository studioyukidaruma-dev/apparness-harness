Hook が強制する 10 ルール

#強制内容発火点Bash 経由
1ハーネス非侵襲性。harness/** .claude/** .github/** は harness/ ブランチでのみ変更可PreToolUse対象
2担当外ガード。worktree ルートの basename ＝ feature-id でなければ拒否（status.yaml は除外）PreToolUse対象
3契約凍結。contract.yaml は NOT_STARTED／CONTRACT_DRAFTED の間のみ変更可PreToolUse対象
4進捗自動再生成。status.yaml／requirements.machine.yaml／architecture.machine.yaml の更新で render_progress.py を起動（非ブロッキング）PostToolUse対象
5必須 Skill の充足。required_skills[].plugin_ref が enabledPlugins に無ければ src/** を書けないPreToolUse対象
6上位文書ガード。worktree からの 00-requirements 01-foundation 02-design 書き込みを常に拒否PreToolUse対象
7要件↔設計の整合。based_on_requirements_version 不一致なら設計を APPROVED にできないPreToolUse対象外
8フェーズ節目のコミット強制。3 つの machine YAML に未コミットがあれば応答終了を拒否Stop / SubagentStop—
9状態遷移の妥当性。直線状態は 1 段階前進のみ。終端は変更不可。BLOCKED は履歴を遡って復元PreToolUse対象外
10検証受領書ゲート。TESTED は受領書の存在・全 exit 0・commit 一致が条件。受領書の手書きは常に拒否PreToolUse対象外

Rule 7・9・10 は Bash 経由の書き込みを判定できない

これらは Edit/Write の「書き込み前後の内容比較」に依存するため、sed -i 等では判定が一度も走らない。 静的検知でパスは拾えるが、書き込み後の内容を予測できないためルールを適用できない。 原則 Bash で書き込む運用では、ここに穴が開く。

監査の着眼点

図から読み取れる、コンテキスト削減と決定論化の候補。いずれも実測・実コードにもとづく。

全文読み CONVENTIONS.md 35.8 KB × 2 フェーズ

.claude/agents/requirements-analyst.md:8 / solution-architect.md:8

両 agent とも「最初に読み」と指示。solution-architect は「特に 6・9・10・11・12・13・14 節」と書くが、 節の抽出は指示されておらず実質全文が入る。常時読み込み予算 36,000 B のほぼ全量を 1 ファイルで消費している。

削減案: 節見出しが ^## N. で統一されているので、 sed -n '/^## 6\./,/^## 7\./p' のような範囲抽出を agent 定義に書けば決定論的に絞れる。

良い前例 feature-builder / gate-reviewer

.claude/agents/feature-builder.md, gate-reviewer.md

feature-builder は CONVENTIONS.md を読まない（必要な規約は agent 定義に内包）。 gate-reviewer は review-rubric.md 4.9 KB だけを判断基準とし、rubric 外の指摘を無効と明記。 フェーズ固有の知識を切り出す方針が既に実践されている箇所。

決定論化の候補 「全機能が TESTED か」

GATE 5 / .claude/agents/integrator.md

現状は PROGRESS.md／STATE.machine.yaml を読んで AI が判断している。 STATE.machine.yaml は構造化済みなので、jq 相当で機械判定できる。

features[] のうち state != TESTED が 1 件でもあれば統合を拒否

記録であってゲートでない gate-reviewer の verdict

CONVENTIONS.md 10 節 Layer 1.6

verdict は Blocker 数の集計で機械的に決まるが、何を Blocker とするかは AI の判断。 さらに結果は status.yaml の review に記録されるだけで、Rule 10 のような機械ゲートにはなっていない （実行の裏付けを持たないため、と規約が明言）。NO-GO のまま TESTED にすることを止める仕組みは無い。

運用ルールのみ code-review / security-review

CONVENTIONS.md 10 節 Layer 1.5

feature-builder は TESTED 前に code-review、integrator は統合前に両方を実行することが 「必須ステップ」とされているが、実行を確かめる Hook も CI 項目も無い。 Skill が見つからない場合はユーザーに報告して先へ進む設計。

コンテキストクリアできる境界

P1 → P2 → P3 → P4 → P5

各フェーズの成果物は全てファイルに落ちる（要件 → 設計 → 契約 → 受領書 → 統合記録）。 フェーズをまたぐ会話の継続は原理的に不要で、次フェーズは成果物ファイルだけを入力にできる。 P4 は worktree ごとに別セッションが必須なので、そこは既に強制的にクリアされている。

穴 Rule 7・9・10 と Bash

harness/hooks/pre_tool_use_guard.py

書き込み前後の内容比較に依存する 3 ルールは Bash 経由で判定が走らない。 決定論化案: status.yaml／requirements.machine.yaml／architecture.machine.yaml への Bash 経由の書き込みを一律拒否し、構造化ツールを要求すれば、内容比較が必ず走る状態にできる。

承認の人間性

GATE 1 / CONVENTIONS.md 9 節

requirements-analyst の frontmatter は AskUserQuestion を宣言しているが実際には渡らない。 承認は「親セッションが人間に聞き、subagent に伝える」伝聞になり、 AI が AI の伝聞を根拠に APPROVED を確定させる経路が標準フローに埋まっている。 承認の書き込みを親セッションの責務に一本化するのが素直な解。
