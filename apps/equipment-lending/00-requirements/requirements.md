# 要件定義: 備品貸出管理

> このファイルは人間向けです。機械向けの構造化データは `requirements.machine.yaml` を参照してください。
> 内容はこの2ファイルで常に一致させてください（`requirements-analyst` subagent が両方同時に更新します）。

- app_id: `equipment-lending`
- version: 1
- status: DRAFT

## 概要 (Summary)

会社の備品の在庫の数を管理するアプリ。現在は貸出を紙で管理しているため、どこに何が何個あるかがすぐ分からない。現場の作業員がスマホのブラウザから、備品の保管場所と在庫数を確認でき、誰がいつ何を借りたか・返したかを登録できる状態にする。データは社内サーバに保存し、全員が同じ在庫状況を見られるようにする。

## 目的 (Goals)

- スマホから在庫がわかる

## やらないこと (Non-Goals)

- 権限管理はしない。

## 想定ユーザー (Target Users)

- 現場の作業員。スマホから入力する。

## 機能要件 (Functional Requirements)

要件ごとに、受け入れ基準まで**この文書にも**書きます（`requirements.machine.yaml` の
`acceptance_criteria` と一字一句同じ文にしてください。契約の `coverage[]` はこの原文を
そのまま引用してテストと対応づけ、機械検証されます）。

### FR-1: 備品の場所確認、在庫数確認

- 優先度: MUST
- 説明: どこに何が何個あるかすぐ確認できる。保管場所は `A棚` `2階倉庫` などの区画をタイル状に並べて表す（地図画像や地図サービスは使わない）。
- 受け入れ基準:
  - 保管場所の区画ごとに、その区画にある備品名と数量が表示される

> 補足: 企画ブリーフの原文は「地図上に、ものと、数が表示される」でした。ヒアリングで「地図」が
> 保管場所の区画表示を指すと確認できたため、検証可能な文に書き換えています（意図は同じです）。

### FR-2: 備品の貸出登録

- 優先度: MUST
- 説明: 誰がいつ何を借りたかを記録する
- 受け入れ基準:
  - 貸出を登録すると、一覧に借用者名と日時が表示される
  - ある作業員が登録した貸出が、別の作業員の画面の一覧にも表示される

### FR-3: 備品の返却登録

- 優先度: MUST
- 説明: 借りた備品を返したことを記録し、在庫数を元に戻す
- 受け入れ基準:
  - 返却を登録すると、その備品の在庫数が貸出登録前の数に戻る

### FR-4: 備品の検索

- 優先度: SHOULD
- 説明: 備品名で絞り込んで目的の備品を探せる
- 受け入れ基準:
  - 備品名の一部を入力して検索すると、一致する備品だけが表示される

### FR-5: 貸出中一覧

- 優先度: SHOULD
- 説明: いま貸し出されたままになっている備品をまとめて確認できる
- 受け入れ基準:
  - 貸出中一覧に、まだ返却されていない貸出が借用者名と日時とともに表示され、返却済みの貸出は表示されない

## 非機能要件 (Non-Functional Requirements)

- セキュリティ: 借用者名（個人情報）を含む貸出履歴に、社外のネットワークから到達できないこと。社内ネットワークからのみアクセスできればよく、ログイン（認証）は設けない。
- データ: 備品情報と貸出履歴はサーバに保存し、全利用者が同じデータを参照できること。
- 規模: 現場作業員 20 名程度・全体で数十名が利用し、同時アクセスは数名を想定する。
- 利用形態: スマホのブラウザから操作することを前提とした画面とする。

## 制約 (Constraints)

- 有償ライセンスのライブラリは使用しない。
- フロントエンドの実装方針は frontend-design skill の方針に寄せる（必須依存としては登録しない）。
- UI あり（ブラウザで動作する画面を持つ）。
- 実行環境はブラウザ。
- オフラインで動作する必要はない。
- 外部サービスとの連携はない。
- 社内サーバに配置する。
- アプリ全体の完成条件は「各機能要件の受け入れ基準がすべて満たされること」とする。
