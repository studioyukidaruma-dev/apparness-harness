§ 0

要旨

総合結論
プロダクトとしての優劣は claude-code-harness が明確に上位。ただし両者は同一の問題を解いていない。

claude-code-harness（以下 CCH）は既存リポジトリでの継続的開発オペレーションを対象とした汎用ハーネスであり、 危険操作の遮断・マルチホスト・配布・非エンジニア向け UI・リリース自動化まで含む完成品である。 apparness はグリーンフィールドのアプリ生成工程に特化した工程ハーネスであり、 対象領域が CCH の 1/5 程度に狭い。したがって「置き換え可能な競合」ではない。

両者が重なる唯一の土俵での評価
「AI が言い抜けできない決定論的強制」という軸に限れば、apparness が単位コード量あたりで優る。

apparness の Rule 10 / Rule 11（検証受領書の HEAD 束縛）と CI 項目 I–K は、 実行結果の内容そのものを検証する。CCH の同等機構（[tdd.enforce]）は 配布既定で enabled = false であり、Worker の self_review は エージェント自身が verified: true と書き込む自己申告である。

本報告書が採る評価原則

「ドキュメントに書いてある」ことは能力の証拠として扱わない。実際に配布物に存在し、 呼び出し経路が確認でき、失敗時にブロックする実装が読み取れるものだけを「強制されている」と判定する。 これは CCH 自身が docs/claims-audit.md で採用している規律をそのまま両者に適用したものである。

§ 2

問題設定の違い — 同一土俵ではない

優劣を論じる前に、両者が守ろうとしている対象が異なることを確定させる。 これを混同すると「apparness には削除ガードが無い」「CCH には要件トレーサビリティが無い」という指摘が、 どちらも「設計上の欠落」なのか「範囲外」なのか判定できなくなる。

観点apparnessclaude-code-harness
解こうとしている問題 「AI にアプリを 0 から作らせると、コンテキスト肥大で精度が落ち、約束事項が守られない」 「AI に実装を任せると、計画が会話に埋もれ、テストが後回しになり、レビューが後追いになり、リリース根拠が記憶頼りになる」

守っている対象 工程の整合性。要件 → 設計 → 契約 → 実装 → 統合という上下関係が壊れないこと マシンとリポジトリの安全、および出荷判断の根拠。危険操作が実行されないこと、証跡が揃わないまま出荷されないこと

帰結

apparness の Hook 11 ルールのうち危険操作を防ぐものは 0 件である。 これは設計範囲の外だが、実運用上は明確な穴になる（§3.3）。 逆に CCH には「要件 ID → 機能 → テスト ID → JUnit XML」という縦の突合が配布物に存在しない。 これも欠陥ではなく、CCH が要件定義フェーズを持たないためである。

§ 3

本報告書の中核。両者とも「AI の自己申告に依存しない」ことを標榜するが、 何を機械が読んで判定しているかの粒度が根本的に異なる。

決定論 受領書の HEAD 束縛

Rule 10 の本質は exit_code: 0 ではなく commit == HEAD の一致条件にある。 これが無ければ「一度通したテスト結果を、実装を書き換えた後も使い回す」ことができてしまう。 CI 側は HEAD が先行しているため、受領書の commit が HEAD の祖先であり、 かつそのコミット以降に機能ディレクトリが未変更という等価条件で再検証する。

CI 項目 I / 検証ランナーが生成、Hook が改変を拒否

決定論 Bash 間接書き込みの二段検知

インプレース編集・コピー・リダイレクト等による迂回に対し、静的検知で未然にブロックし、 取りこぼしを事後検証が実行前後の内容ハッシュ比較で捕捉して実行直前の内容へ巻き戻す。 この検知に解除用の環境変数は意図的に用意されていない——AI 自身が解除できれば決定論的強制の目的が崩れるため。

PreToolUse 静的検知 ＋ PostToolUse 事後検証

決定論 worktree スコープの読み替え

worktree を通るパスは当該 worktree 基準に読み替えてから Rule に掛ける。 読み替えを欠くと機能ディレクトリにアンカーされた Rule 1・2・3・5・9・10 がまとめて素通りする。 これは実装上の理屈ではなくドッグフーディングで実証された実害である （F-029/F-030: メインセッションから受領書なしで state: TESTED を書き込めていた）。

ドッグフーディング記録 F-029 / F-030、ガイド §5

Hook はローカルの Claude Code プロセス内でしか効かない。apparness は同じ判定を GitHub Actions 上で項目 A–O として再実行する（3 ジョブ: セルフテスト・規約チェック・脆弱性スキャン）。 脆弱性スキャナはバージョン固定＋SHA-256 検証で導入される。

共通の構造的弱点: 起動失敗時の fail-open

CCH の起動 shim は、対象プラットフォームのバイナリが見つからないとき stderr に診断を出して exit 0・stdout 空で終了する（Claude Code はこれを「判断なし＝通過」と解釈する）。 hooks 定義側も plugin root を特定できない場合は skip して exit 0 する。 これは UX 上の意図的な選択だが、「外せない実行時フロア」という主張はバイナリが実在し実行可能であることを前提にしている。 apparness も python3 が PATH に無ければ同じ状態になる。 いずれのハーネスも、強制レイヤの健全性を起動時に自己診断する仕組みを持たない点で同じ穴を持つ。

本調査中に観測した apparness の誤検知（実データ）

本報告書を生成する過程で、リポジトリルート直下の HTML ファイルを heredoc 経由で書き出そうとしたところ、 apparness の PreToolUse ガードがハーネス本体への書き込みとして拒否した。 原因は、静的検知がヒアドキュメントの本文とコマンド引数を区別せず、 HTML の本文中に現れたハーネス配下のパス文字列を書き込み対象候補として抽出したためである。 規約 §7 は「誤検知を見つけたら検知ロジック自体を修正する」と定めており、 これはその手順に載せるべき実測サンプルにあたる（改修方針 P1-3 に反映）。 なお安全側への誤りであり、構造化ツール（Write）に切り替えることで正しく書き込めた点は、 規約が意図した回避経路どおりに動いている。

§ 4

監査可能性とサプライチェーン

A apparness — 全文可読・依存ゼロ

  • 強制ロジックは Python 標準ライブラリのみ（hooks 2,189 行）。第三者が全文を読める
  • スクリプト群は PyYAML / jsonschema のみに依存
  • 判定ロジックに対する pytest 3,819 行が同梱され、CI で実行される
  • 脆弱性スキャナをバージョン固定＋SHA-256 検証で導入（サプライチェーン規律あり）

実測: Python ソース総行数 5,330 行

B CCH — バイナリ配布・ソース不同梱

  • 配布 zip（642 エントリ）に Go ソースツリーのエントリが 0 件。go.work は当該ディレクトリの使用を宣言するが実体が存在しない
  • ガードレール判定は 13 MB の Go バイナリ 4 本のみ。ソースからの再現ビルドが利用者側で不可能
  • scorecard.yml は binary-artifacts チェックを remediated と注記（「リリースビルドとバイナリメタデータは別途検証」）
  • 配布物にテストが無く、導入後の自己検証手段が doctor サブコマンドに限られる
  • README は「記述が機械で検査されている」と主張するが、その検査自体も配布物には含まれない

実測: 配布 zip 内の Go ソースエントリ数 = 0

評価

監査可能性は apparness が明確に優る。 「AI に自分を縛らせる」システムでは、縛る側のコードが読めることの価値は大きい。 ただしこれは配布形態の差でもあり、CCH の GitHub リポジトリ本体には Go ソースが存在する可能性が高い （.gitignore はビルド成果物とチェックサムのみを除外しており、ソースツリー自体は除外していない）。 本報告書が判定できるのは「手元の配布物では検証不能」という事実までである—— これは CCH 自身の not_observed != absent 原則に従った記述である。

CCH の self_review の構造的限界

CCH は Worker に 6 つの自己検証ルール（DRY 違反ゼロ・宣言シンボルの呼び出し経路・既存テスト回帰なし等）を課し、 {rule, verified: true, evidence: "<実コマンド出力>"} の形で返させる。 Lead は verified=false または evidence="" があれば自動差し戻す。 これは形式としては優れているが、verified も evidence もエージェント自身が書く文字列であり、 Lead がそれを実行して再現するわけではない。 apparness の受領書は検証ランナーが実際にサブプロセスを起動して終了コードを記録したものであり、 AI がその内容を Edit/Write で書き換えようとすると Rule 10 が常時拒否する。 「証拠を語る」と「証拠を作らせない」の差である。

規約本体の残余は 109 バイト、feature-builder は 19 バイト。 さらに項目 O が新節の追加を拒否する。 つまり「Rule を 1 本足す」という最も自然な改修が、現状では CI 落ちを引き起こす。 改修に先立って説明文のガイドへの移設による予算の再配分が必須であり、 これは技術的負債ではなく設計どおりに機能している制約だが、次の改修サイクルの最初の作業項目になる。

apparness の gate-reviewer の設計は CCH より厳密

CCH のレビューは多角的だが、最終 verdict は LLM の判断である。 apparness は Blocker が 1 件以上なら NO-GO、0 件なら GO と集計から機械的に決定し、 1 ラウンド最大 5 件・3 ラウンド NO-GO で人間へエスカレーション、 レビューアに Write / Edit を与えない（直すのは実装者の責務）と定めている。 さらに rubric 外の指摘を無効とすることでレビューの発散を防いでいる。 規模は小さいが、LLM 判断を機械的な集計規則で包むという設計は CCH の invariant 1 （「決定論的検査が拘束力を持ち、LLM の意味論レビューは助言のみ」）を、より小さいコードで実現している。

§ 8

認識論的規律 — CCH から学ぶべき最大の資産

not_observed != absent

「観測していないこと」を「無いこと」と結論しない。手元に証拠が無いのは「ここでは証明できていない」という意味であり、不可能でも対応済みでもない。ホスト対応表・機能表のすべての行にこの原則が適用されている。

False Parity Rule

同じ capability 名でも enforcement 強度はホストごとに違う。「Cursor は deny できるが FS jail は無い」「Codex の hook は Bash のみ」を表の中で明示する。強みを均して見せることを禁止している。

claims-audit

公開向けの主張を「いま証明済みか / 追加証跡が必要か」で分類する監査表。README を更新するときは先にこの表を見直す。自社の目玉機能を "Not yet safe to claim strongly" と自己格下げしている行がある。

known-limitations

Harness の制御外に根本原因がある問題を、症状 / 根本原因 / 適用中の緩和策 / 再検討の条件の 4 点セットで記録。モデル側の safeguard がレビューを中断させる問題まで書いてある。

apparness 側の対応物

apparness はガイド §7 に「決定論 vs AI 判断 対照表」を、§11 に「既知の制約」を持っており、思想としては同型である。 さらにドッグフーディング記録は 77 件の摩擦点を深刻度つきで記録し、 「決定論的強制の中核が空振りしていた」（F-029/F-030）という自分にとって最も不利な事実を第一級の記録として残している。 これは claims-audit と同じ規律である。 不足しているのは「対照表の各行が今も本当に効いていることの継続的な証跡」—— Rule ごとの「実際にブロックすることを実証するテスト」への紐付けが体系化されていない点である。

§ 11

結論と適用指針

問い: どちらが優れたハーネスか
汎用の開発ハーネスとしては claude-code-harness が優れている。決定論的な工程強制の核としては apparness が優れている。両者は補完関係にある。
  • 既存リポジトリでの日々の開発を安全に回したい → CCH。apparness は原理的に使えない。
  • 新規アプリを、要件から統合まで工程として強制しながら生成したい → apparness。CCH には要件・設計・機能契約という上下関係の概念がない。
  • AI の「やりました」を信用しない仕組みが欲しい → apparness の Rule 10 / 11 が現時点でより厳密。CCH の TDD 強制は配布既定で無効。
  • AI に危険な操作をさせたくない → CCH。apparness には該当ルールが 1 件も存在しない。

apparness にとっての最大のリスクは「CCH に劣ること」ではない

apparness の差別化は内容検証型ゲートにあり、これは CCH が持っていない。 危険なのは、CCH に追いつこうとして機能数・スキル数・ドキュメント量で張り合い、 項目 L / M / O という自らの防波堤を緩めてしまうことである。 CCH の 87,547 行・143 docs という規模は強みであると同時に、 認知負荷を扱う文書の存在が示すとおり、それ自体が管理対象の問題になっている。 apparness が取り込むべきはCCH の機能ではなく、CCH が押さえている脅威—— すなわち危険操作の遮断と、強制レイヤ自身の健全性検証である。

具体的な改修方針は、同時に生成した IMPROVEMENT-PLAN.md（人間向け）と IMPROVEMENT-PLAN.machine.yaml（AI 向け）を参照。
